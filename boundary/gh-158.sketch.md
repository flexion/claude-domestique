# Implementation notes — gh-158

NOT NORMATIVE. Not referenced by the boundary and not part of it.

Refinement states what must be true. How to build it is the next phase, and these
are notes for that phase. Nothing here gates anything.

## Change surface

```
modus/prompts/author-boundary.md               the Author's drafting prompt
modus/scripts/draft-boundary.js                renders it, validates the result
modus/scripts/__tests__/draft-boundary.test.js
boundary/gh-158.yaml, boundary/gh-158.sketch.md   this boundary itself
```

Anything else is out of scope.

## Input

The script does **not** fetch from any tracker. Fetching is adapter work and belongs
to gh-156. Input arrives as a JSON document on a path or on stdin:

```json
{
  "item_ref": "gh-158",
  "tracker": "github-issues",
  "parts": [
    { "id": "description#1", "text": "..." },
    { "id": "description#2", "text": "..." }
  ]
}
```

`parts[].id` is `<field>#<n>`, one-based, paragraph-level within a field. Paragraph
granularity is the working answer and it is known to be inadequate for short items —
see `domestique-3lf`. The script does not invent parts, split sentences, or reorder
them; it addresses what it is given.

## Output

Writes `boundary/<item_ref>.yaml`. Refuses to overwrite an existing file unless
`--force` is passed. A silent overwrite of a frozen boundary would remove the
freeze without recording that it happened.

Drafts a **candidate only**. It never approves, never freezes, never commits, and
never marks a boundary frozen. A human does that, per gh-158's own goal.

## Validation

Requires `modus/scripts/lint-boundary.js` and calls `lintBoundary(doc, { itemParts })`
with `itemParts` taken from the input's `parts[].id`. Passing the part list is
required, not optional: without it every `item_locator` check exempts itself and the
draft is unvalidated where it matters most.

Exit codes follow the three-outcome rule in the modus README:

| Exit | Meaning |
|---|---|
| `0` | draft written, lints with no failures |
| `1` | draft written, lints with failures — they are printed and the file is kept for editing |
| `2` | could not run: input unreadable, malformed, or no parts supplied. Names the cause. Writes nothing |

Exit `2` writes nothing. A partial file at the boundary path would be read by the
next step as a boundary.

## Semantic correspondence

The anti-boilerplate requirement, and the reason AC-1 and AC-2 in the manifest are
not sufficient on their own.

- Every `claims[].id` referenced in `interpretation.claim_provenance` carries at least
  one `item_locator` support whose `ref` resolves to a supplied part.
- Changing the text of an input part changes the drafted `goal`, `problem`, or at least
  one claim. A draft that is invariant under its input is boilerplate wearing a schema.
- Copying input text into a comment or an unread field does not satisfy either rule.

The tests for this are mutation tests: perturb one input part, assert the named output
fields differ. An adversarial fixture — a static, well-formed, gh-158-shaped manifest
that ignores its input entirely — must fail them.
